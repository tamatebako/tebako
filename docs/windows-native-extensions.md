# Windows native extensions: the build chain, end to end

This document records how a tebako press on Windows builds a Ruby
native extension (a C extension compiled against the runtime SDK) and
boots it inside the packaged executable. Every mechanism here was
established by evidence during the Rails-on-Windows work (issue #753,
closed green at v2.8.44), and each section names the defect class it
guards against so the reasoning survives the people who learned it.

The companion walkthrough for a full application is
`docs/rails-packaging.md`.

## The runtime's shape: a loader and a DLL

The Windows runtime is two artifacts, not one. The executable
(`tebako-runtime-<ver>-ruby-<ver>-windows-ucrt64.exe`) is a 99 KB
loader that imports the interpreter proper, `x64-ucrt-ruby340.dll`,
which carries every Ruby symbol — roughly 3,400 exported names from a
50 MB image. The DLL rides the machine-wide store beside the
executable, materialized at first run under its manifest-declared PE
name.

The split explains the most confusing failure class of the whole
chain: a symbol that the executable's `nm` output seems to lack is
usually a DLL symbol, and a link surface built from the wrong binary
fails on nearly everything.

## The SDK: the configure replay

The runtime SDK regenerates the header tree a native extension needs
by replaying the runtime's own recorded `./configure` invocation
against the patched Ruby source tarball. On Windows the replay runs
under an explicitly resolved msys bash, with the mingw toolchain
pinned, with the generated configure's cache-eval probes patched to
space-safe form, and with `--disable-shared` forced. Each of those
four pins closes a defect that cost a release cycle to find:

* **The shell is resolved by name and directory, never a bare
  invocation.** `sh` reaches Git's POSIX-mode shell, and a bare `bash`
  reaches `C:\Windows\System32\bash.exe`, the WSL launcher stub, which
  prints a UTF-16 banner and exits. The resolver takes the Ruby
  DevKit's msys bash, or the first `bash.exe` on `PATH` outside the
  Windows system directories, and fails with a named error when
  neither exists.
* **The compiler is pinned to `CC=gcc`, `CXX=g++`.** configure's own
  search finds the runner image's LLVM clang, which drives the MSVC
  linker; that linker has no POSIX symbols, and every probe that
  mentions `gettimeofday` dies together.
* **The generated configure's cache-eval probes are patched.** The
  upstream generator concatenates a C type name into a shell variable
  name — ucrt's `ssize_t` is `long long`, so the name carries a space
  — and msys bash aborts the whole script on the invalid expansion.
  The patch rewrites both eval forms to build the correct autoconf
  cache name and expand it indirectly; the rewrite is count-guarded
  so a drifted tarball fails by name rather than silently unpatched.
* **The replay builds static.** The runtime ships no import library in
  its store, and configure's shared-libruby default makes the
  generated headers declare `dllimport`, which produces `__imp_`
  references nothing in the process satisfies.

## The link surface: the DLL's true export table

mkmf's link probes need a real archive to resolve against, and the
SDK provides two. The symbol stub (a plain-thunk archive of the
runtime's exported names) keeps probe resolution honest on POSIX. On
Windows the load-bearing artifact is the import library,
`libruby.dll.a`, generated by `dlltool` from a `.def` — and the `.def`
must carry the DLL's **true export table** (`objdump -p`'s
`[Ordinal/Name Pointer] Table`), never `nm`'s global-symbol list.

The distinction is the sharpest lesson of the chain. The DLL defines
roughly 44,000 global symbols but exports only 3,400. A `.def` built
from the globals includes CRT internals (`memcpy`, `Sleep`,
`_initterm`, `DllMain`), and `dlltool` turns each into a thunk that
binds the extension's CRT references onto the Ruby DLL at link time.
The loader then cannot find those procedures at boot — Windows error
127, "The specified procedure could not be found" — because the DLL
never exported them. The failure appears two releases later in a
different costume if the poisoned `.def` instead trips
multiple-definition conflicts at link. The true-export table contains
no CRT internals, so the system CRT keeps those references and the
boot binds cleanly.

The export-table `.def` answers both symbol spellings by
construction: import libraries provide `__imp_<name>` thunks and
plain aliases together, so it does not matter which DECLSPEC mode a
probe-driven compile lands in. During the chain two consecutive
verdict legs alternated between plain and `__imp_` references under
identical headers — the mkmf probe outcome selects the mode, which is
why the link surface must cover both rather than chase one.

## The deploy vehicles

The press runs its gem installation inside the runtime through a
driver script, and the child processes that mkmf spawns (`extconf.rb`)
re-enter the runtime through a real executable. On Windows that
vehicle is `ruby.exe` — the press's own bootstrap bytes stitched with
the deploy driver image, so the spawn's explicit `.exe` spelling
answers, and the trailer's `;image` ref resolves the exact cached
runtime pair without a network round trip.

The vehicle's trailer mounts the deploy image at its own point
(`/__tebako_deploy__`), never at the runtime root. The parent deploy
driver — which runs without an env image and needs ruby's load paths
to resolve into the deploy image itself — keeps the runtime-root
mount. A second image at the runtime root would union over the env
image's copy of the in-image manifest and misattribute its library
aliases, a defect recorded as issue #825.

Every path value that crosses into a Ruby source or a spawned command
line is forward-slashed. The cmd.exe and sh.exe layers strip
backslashes from spawn strings, which turns
`C:\Users\runneradmin\...` into `C:Usersrunneradmin...` — a filename
that exists nowhere.

## The instrument: five-minute probes

Each defect above was separated from its neighbors by a runner probe
rather than a release cycle: a small dispatch workflow
(`deploy-probe.yml`) that presses real bytes through the pinned
toolchain and prints the one artifact under suspicion. The scenario
scripts live in `tools/probes/` (`press-gem`, `dissect-sdk`,
`child-boot`), and the Rails verdict leg accepts a `tools_run` input
that presses a release run's staged, gate-passed tool bytes before
they publish. A fix-to-verdict loop that once took a release (roughly
two hours) takes a run (roughly forty-five minutes), and a diagnosis
that once took a release takes five minutes.
